Grounding Context

Codebase context. Context Engine is FastAPI + Next.js with a Local Studio–parity Settings shell at /settings. Current sections: General, Model Provider, Domains, Users. A comment cites an F-010 gate for controller/storage/hardware/plugins/skills — Setup is not named there. Compose stack pillars are postgres, migrate, api, worker, frontend. Worker liveness is heartbeat freshness; smoke oracles include postgres_health, alembic_head, worker_healthy. Host scripts/dev.sh is not the full compose stack.

Parity target (corrected). .reference-LS-frontend/templates/nextjs-feature-demos/features/settings-panel — section id setup, SettingsGroup title="Setup checks", rows from SetupCheckRow { id, label, status, detail }, StatusPill tones. LS fixture content (Pi, controller URL, ~/models) must not ship in CE live status.

Past learnings. Runnable-stack compound doc: one lease-poller worker; shared volumes; status/id-only evidence; no Redis/RQ/Celery.

External context. Calm readiness panels beat mini-Portainer; overall verdict + checklist; separate liveness from readiness; dependency-order explanations.

1 · TOP PICK

LS Setup checks chrome, CE pillar cargo

Conf 92% Complexity Medium axis: reference-setup-ui-parity
Description
Add an admin setup section to the existing Settings state nav (no new top-level route). Render exactly like the reference settings-panel Setup: SettingsGroup “Setup checks”, SettingsRow + monospace detail + StatusPill for ok|warning|error. Replace LS fixture rows (Pi, controller URL, directories) with CE stack pillars. Unlock is justified: the F-010 comment never named Setup; F-009 gates the setup-wizard, not this readiness board.
Basis
direct: reference Setup render and SetupCheckRow type; CE SettingsPanel already imports LS primitives and uses React section state; F-010 absent-list omits Setup.
Rationale
Delivers the user’s asked parity target inside the shell that already exists, without waiting on blocked operator surfaces.
Downsides
Needs a safe status API before live data; until then fixture/stub rows risk teaching wrong semantics. Hash deep-links (LS) are optional and can wait.
2

Redaction-first Setup status contract (reason codes)

Conf 90% Complexity Medium axis: safe-status-api-contracts
Description
Ship a narrow admin Setup status DTO: check id, status enum, and a closed set of detailCode values the UI maps to copy. Never return runtime URLs, paths, stack traces, or raw healthcheck output. Internally map from smoke-style oracles; publicly speak reason codes that would pass a safety scan.
Basis
direct: AGENTS.md redaction rules; stack evidence status/id-only; LS fixtures show exactly the URL/path detail style CE must not copy.
Rationale
Makes the safe path the easy path and unblocks UI parity without inventing a Portainer surface.
Downsides
Closed lexicon needs a small contract patch; less “raw diagnostic” power for power users (acceptable for Settings).
3

Mode-graded certificates: host-dev vs compose

Conf 88% Complexity Medium axis: host-vs-compose-modes
Description
First signal is runtime mode (compose-stack | host-dev | unknown). In host-dev, compose-only pillars are not_applicable / warning — not danger. In compose, the same absences are danger. Same Setup UI, different expectation matrix. Never leak which API base DNS name is in use.
Basis
direct: scripts/dev.sh does not start compose worker/postgres; compose frontend uses http://api:8000 vs host 127.0.0.1:8000.
Rationale
Prevents false-red Setup for host developers and preserves real alarms for compose operators.
Downsides
Mode detection must be honest; mis-detection trains users to ignore the panel.
4

Dependency-ordered five-channel GO/NO-GO poll

Conf 85% Complexity Medium axis: stack-pillars-status
Description
List pillars in bring-up order: postgres → migrate → api + worker → frontend. Treat migrate as a one-shot gate (alembic_head), not a forever-live service. Continuous channels (postgres/api/worker) use ongoing readiness. Detail copy explains the next blocker without Docker internals.
Basis
direct: canonical compose service set; smoke oracles; external readiness-vs-liveness pattern.
Rationale
Turns “something is up but the app does nothing” into a readable blocking path.
Downsides
Ordering UI is slightly more complex than a flat list; must not imply the frontend can control Docker.
5

Worker heartbeat freshness as lease-poller truth

Conf 90% Complexity Low axis: stack-pillars-status
Description
Worker row means “lease poller heartbeat within window,” not “container exists.” Map stale/absent heartbeat to warning/error with safe detail codes. Never expose the heartbeat file path.
Basis
direct: compose worker healthcheck on heartbeat mtime < 30s; runnable-stack learning that missing worker yields a login shell with queued uploads.
Rationale
Surfaces the failure mode that made the stack worthless, in the place admins already look.
Downsides
Long run_once work can briefly look stale — copy should avoid panic on transient lag.
6

Acceptance-traceable Setup rows

Conf 78% Complexity Low axis: safe-status-api-contracts
Description
Every Setup row maps to one pillar, one oracle, one contract-safe field, and one test expectation. PRs that add a check must answer those four questions.
Basis
direct: smoke + safety-scan discipline already used for stack evidence; status/id-only JSON rule.
Rationale
Compounds governance so Setup cannot grow into an unsafe dump of ops strings.
Downsides
Slight process overhead; may feel heavy for a first slice if over-applied.
7

Read-only stack mirror — not a setup wizard

Conf 86% Complexity Low axis: reference-setup-ui-parity
Description
Keep the LS Setup look, invert the product meaning: non-interactive readiness board for stack pillars. No install actions, no Docker controls, no Logs/Usage/Node — those stay F-010-blocked.
Basis
direct: F-010 AC-007 blocks richer operator UI; F-009 hides setup-wizard; Settings shell already status-oriented with StatusPill.
Rationale
Clarifies scope so parity work does not accidentally import Local Studio’s first-run wizard semantics.
Downsides
Users may expect “fix” buttons; guidance must point to compose/dev docs, not in-app remediation.
